# Security review and login transport — alpha.6

This is a bounded source, dependency and installed-runtime review, not a claim that the project is vulnerability-free or a replacement for an independent penetration test. No hostile testing was directed at third-party hosts. Temporary accounts and files were used; passwords and session cookies were not recorded.

## Findings and changes

- **Existing web access survived a Linux account lock or password change.** Reproduced on the installed earlier release. Sessions now carry a one-way fingerprint of the root-readable local shadow record, checked on authenticated requests and active streams. Locked/empty-password/expired accounts and forced password changes fail closed; password/policy changes invalidate old web sessions. New login remains PAM-authenticated. The fingerprint is separate from the Linux identity binding, so ordinary password changes do not delete app grants. First deployment requires reauthentication for pre-fingerprint web sessions; user processes remain alive.
- **Authentication services allowed core dumps.** Broker and gateway now have `LimitCORE=0`, inherited by the PAM helper. Credentials still cross only HTTPS, loopback and private Unix/pipe boundaries; they are never put in commands, logs or frontend storage.
- **Login inherited the file-upload body allowance.** Gateway and broker now read at most 4096 bytes, including chunked bodies, before rejecting oversized requests. Compressed HTTP request auto-decompression is disabled in these services to avoid expanding unauthenticated bodies. Malformed/non-object login JSON is rejected. File upload limits remain separate.
- **The distribution aiohttp version had published parser/WebSocket issues.** New gateway, broker and workers use a separate root-owned Python environment pinned to aiohttp3.14.3 and the dependency versions in `deploy/python-runtime.txt`. These include upstream fixes for CVE-2026-69243, CVE-2026-69244 and CVE-2026-59881. System Python is unchanged. Existing occupied workers retain their loaded libraries until they are retired; their authenticated routing is protected by the updated broker, and their sockets remain UID-private. See [Debian's parser advisory](https://security-tracker.debian.org/tracker/CVE-2026-69243), [response-parser advisory](https://security-tracker.debian.org/tracker/CVE-2026-69244) and [WebSocket advisory](https://security-tracker.debian.org/tracker/CVE-2026-59881).

The installed Chromium and libpng packages were updated using the distribution packages. A running browser retains its old executable mapping until explicitly restarted. Do not stop occupied browser/worker services as a side effect of package installation. Deployment evidence must distinguish installed versions from running processes.

## Encryption

The development deployment and fresh dedicated-host Caddy template require TLS1.3. Verified certificate-authenticated connections negotiate TLS_AES_128_GCM_SHA256; earlier TLS versions are refused. A catch-all TLS policy also covers clients without SNI (especially direct IP connections); setting a host-only policy is insufficient for that case. HTTP redirects to HTTPS, and session cookies use Secure, HttpOnly, SameSite=Strict and the __Host prefix. Clients must trust the actual local CA; bypassing certificate warnings is not certificate authentication.

TLS1.2 with modern AEAD/ECDHE was already a sound configuration; TLS1.3 narrows the accepted protocol surface for this modern-browser application. No custom JavaScript password encryption was added. Linux PAM verifies passwords against the OS password store (yescrypt confirmed on the development host); password hashing and network transport encryption are different controls. Session tokens use 256 bits of random input and are stored hashed. [Caddy TLS documentation](https://caddyserver.com/docs/caddyfile/directives/tls) and [OWASP transport guidance](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html) informed the review.

## Verification and limits

Regression tests cover credential-change invalidation, locked/expired accounts, fragmented and oversized login bodies, token storage/expiry, path/symlink/hardlink isolation and package capabilities. Installed TLS/PAM checks cover secure cookies, account lock/password change and live WebSocket revocation with the terminal process preserved, malformed and oversized chunked login, HOME and terminal-start path traversal, two-account ownership/isolation, supplied identity rejection, Origin/CSRF, private worker sockets, logout/root denial and throttling. Dependency audits reported no known advisories for the pinned npm/Python sets at review time; this is time-specific.

Caddy's Debian security package was checked against its tracker. The remaining configuration-dependent rewrite/file-server/request-body-placeholder advisories do not apply to the deployed reverse-proxy-only configuration, which uses none of those features. This does not clear every possible Go/Caddy vulnerability. MFA/passkeys, broader abuse/load testing, PAM identity providers other than local shadow-backed accounts, cross-distribution installation and an independent security assessment remain outside this review.

## Permission revocation source fix — 2026-10-03

The permission endpoint previously deleted the bare app ID while active grants used `app@revision`. Revocation returned success but retained file and notification access; repeated approval could fail on a duplicate database key. Grant replacement now removes legacy and revision-bound rows for only the authenticated user's app inside one transaction. Failed replacement restores the previous grants.

Eight HTTP regression tests exercise the production permission handler and capability check with isolated authentication fixtures and SQLite state: revoked calls are denied, repeated approval and reapproval succeed, stale revisions and unsupported capabilities are rejected, other users/apps are preserved, and insertion failure rolls back. These source tests do not replace installed HTTPS/PAM acceptance.
